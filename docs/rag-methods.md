# Методы построения RAG: карта вариантов и выбор для Partner-Agent

Документ отвечает на два вопроса:

1. какие вообще есть способы строить RAG-систему;
2. какой набор методов даст максимальный эффект именно в нашем кейсе —
   ассистент по компании-партнёру, база неизвестна заранее, ответы должны быть
   со ссылками, работа должна быть быстрой и экономной.

Реализовывать всё перечисленное не нужно: ниже сравнение, ориентиры по эффекту
и стоимости, а в конце — рекомендуемый стек и план проверки.

---

## 1. Оси выбора

Любой метод стоит оценивать по четырём осям:

| Ось | Что значит | Почему важно |
|---|---|---|
| **Качество** | находит ли нужное и не врёт ли | пользователь приходит за фактами |
| **Цена** | токены на запрос (контекст + генерация) | у партнёра может быть много запросов |
| **Скорость** | задержка до первого токена | чат-интерфейс не прощает 10+ секунд |
| **Сложность** | инженерные и эксплуатационные затраты | команда маленькая, база меняется |

Почти все «продвинутые» методы улучшают качество за счёт цены и/или сложности.
Поэтому выбор — это не «взять всё», а «взять то, что даёт прирост на наших данных».

## 2. Каталог методов

### 2.1. Индексация: как нарезать и хранить знания

| Метод | Суть | Плюсы | Минусы |
|---|---|---|---|
| **Фиксированные чанки** (naive) | текст режется по 500–1000 символов с перекрытием | просто, быстро, дёшево | рвёт смысл на границах, теряет контекст |
| **Semantic chunking** | границы по смене темы (эмбеддинги соседних предложений) | чанки цельные по смыслу | дороже индексация, нестабильно на коротких текстах |
| **Proposition-based** | документ разбивается на атомарные утверждения | высокая точность фактов | много чанков, теряются связи, дорого |
| **Parent-child (small-to-big)** | ищем по мелким чанкам, в модель отдаём родительский раздел | точный поиск + полный контекст | два уровня хранения, сложнее обновление |
| **Contextual chunk headers** | к каждому чанку приписывается «где он в документе» (компания, раздел, продукт) | резко снижает потерю контекста, дёшево | нужно генерировать заголовки при индексации |
| **Multi-vector** | у документа несколько векторов: саммари + куски | находит и общие вопросы, и детали | больше векторов и денег |
| **RAPTOR** | рекурсивная кластеризация и суммаризация в дерево | отвечает на обзорные вопросы по большой базе | дорогая переиндексация, сложно объяснить ссылку |
| **GraphRAG** | граф сущностей и связей + суммаризация сообществ | отвечает на «связано ли X и Y», многошаговые связи | дорого, тяжело поддерживать, избыточно для малой базы |
| **Layout-aware / multimodal** | парсинг PDF по блокам, таблицы и картинки как отдельные единицы | таблицы и сканы не превращаются в кашу | нужен серьёзный парсер (docling, unstructured, ColPali) |

Для Partner-Agent важнее всего **contextual headers** и **parent-child**: материалы
компании — это документы с разделами, и обрыв контекста на границе чанка — главная
причина неверных ответов.

### 2.2. Запрос: как улучшить вопрос до поиска

| Метод | Суть | Когда даёт прирост |
|---|---|---|
| **Query rewriting** | переформулировать вопрос в поисковую фразу | разговорные вопросы, местоимения («а сколько он стоит?») |
| **Multi-query** | 3–5 переформулировок, объединить результаты | короткие и неоднозначные вопросы |
| **HyDE** | сгенерировать гипотетический ответ и искать по нему | вопрос не похож на текст документа |
| **Query decomposition** | разбить сложный вопрос на подвопросы | «сравни тарифы и условия поддержки» |
| **Routing / adaptive RAG** | классификатор решает: без поиска / один поиск / многошаговый | смешанный поток простых и сложных вопросов |
| **Step-back** | сначала общий вопрос, потом частный | вопросы про принципы и правила |

Главный риск здесь — **дрейф смысла**: переформулировка может увести поиск в
сторону. Поэтому rewriting стоит применять только к «плохим» запросам
(коротким, с местоимениями), а не ко всем.

### 2.3. Поиск

| Метод | Суть | Плюсы | Минусы |
|---|---|---|---|
| **Dense (эмбеддинги)** | косинусная близость | синонимы, перефразировки, мультиязычность | плохо ловит точные имена и артикулы |
| **Sparse (BM25)** | совпадение слов | точные названия, коды, цифры | не понимает синонимы |
| **Hybrid + RRF** | объединение dense и sparse по рангам | лучше обоих по отдельности | нужно два индекса |
| **Entity boost** | поднять документы упомянутой сущности | вопросы про конкретный продукт/человека | нужен справочник сущностей |
| **Metadata filtering** | фильтр по отделу, дате, типу документа | убирает нерелевантные пласты | требует аккуратных метаданных |
| **Late interaction (ColBERT)** | токенные векторы и MaxSim | очень точный поиск | тяжёлый индекс, дорогая инфраструктура |
| **Fine-tuned embeddings** | дообучение на парах «вопрос-документ» | +5–15% recall на своём домене | нужен датасет и GPU |

Для небольшой базы компании **hybrid + entity boost** — базовый уровень, который
уже даёт основную часть качества. Fine-tuning оправдан только при накоплении
реальных вопросов пользователей.

### 2.4. Постобработка выдачи

| Метод | Суть | Эффект |
|---|---|---|
| **Cross-encoder rerank** | пересчитать top-20 моделью-ранжировщиком | самый предсказуемый прирост точности: обычно +10–20% nDCG |
| **Compression / extractive** | оставить в чанке только релевантные предложения | −30–50% токенов контекста |
| **Deduplication** | убрать почти одинаковые фрагменты | экономия без потери качества |
| **Diversity (MMR)** | не отдавать 5 кусков одного документа | шире покрытие вопроса |
| **Citation grounding** | привязать утверждение к конкретному фрагменту | проверяемость ответа |

Rerank — лучший «рубль за качество» после hybrid-поиска. Он не требует менять
индексацию и легко откатывается.

### 2.5. Генерация и контроль качества

| Метод | Суть | Плюсы | Минусы |
|---|---|---|---|
| **Naive generate** | один вызов с контекстом | дёшево и быстро | нет самопроверки |
| **Self-RAG** | модель сама решает, нужен ли поиск, и критикует свой ответ | меньше галлюцинаций | сложнее промпт, дороже |
| **CRAG (corrective)** | оценка качества выдачи + fallback (веб-поиск/уточнение) | не отвечает по мусору | нужен внешний fallback |
| **Reflection / critique loop** | второй проход «проверь ответ по источникам» | ловит выдуманные факты | +1 вызов, +задержка |
| **Agentic RAG** | цикл инструментов, уточняющих запросов | сильные многошаговые ответы | дорого, непредсказуемо по времени |
| **Constrained decoding / JSON-mode** | жёсткий формат ответа | удобно парсить | не улучшает факты |

Для кейса с обязательными цитатами полезнее всего **reflection с проверкой
цитат**, а не полный Self-RAG: один дешёвый проход «каждое утверждение имеет
источник» отсекает основную часть галлюцинаций.

### 2.6. Память, кэш и экономия

| Метод | Суть | Эффект |
|---|---|---|
| **История диалога** | хранить реплики и подмешивать в промпт | связный диалог |
| **Summary memory** | сжимать старые реплики в саммари | длинные диалоги без роста токенов |
| **Точный кэш ответов** | одинаковый вопрос → готовый ответ | −100% токенов на повторе |
| **Семантический кэш** | близкий вопрос → готовый ответ | −100% токенов, нужен порог и защита от ложных попаданий |
| **Кэш эмбеддингов/поиска** | не пересчитывать запрос | −10–30% задержки |
| **Prompt caching** (провайдер) | система + контекст кэшируются на стороне API | −50–90% цены на повторяющемся префиксе |
| **Малые модели для подзадач** | rewrite/rerank/классификация на дешёвой модели | экономия на «умной» модели |

В нашем проекте уже есть история, точный и семантический кэш с TTL; следующий
шаг по экономии — prompt caching у провайдера и дешёвая модель для переписывания
запроса.

### 2.7. Специальные расширения

| Метод | Когда нужен |
|---|---|
| **Text-to-SQL / structured** | есть таблицы (прайсы, каталоги) и нужны точные агрегаты |
| **GraphRAG** | вопросы про связи: «кто с кем работал», «что входит в…» |
| **Multimodal** | презентации, схемы, сканы договоров |
| **Web fallback (CRAG)** | база не покрывает вопрос, но есть открытые источники |
| **Federated / multi-index** | разные пласты знаний (сайт, Confluence, CRM) с разными правами |

## 3. Сравнение по эффекту и стоимости

Оценки — ориентиры по опыту внедрений, а не гарантия; их надо проверять на своих
данных.

| Метод | Прирост качества | Цена | Сложность | Когда брать |
|---|---|---|---|---|
| Hybrid (dense + BM25 + RRF) | высокий | низкая | низкая | **всегда** |
| Entity boost | средний | низкая | низкая | есть сущности (продукты, люди) |
| Contextual headers | высокий | низкая (на индексации) | низкая | документы с разделами |
| Parent-child | средний | средняя (контекст) | средняя | длинные документы |
| Cross-encoder rerank | высокий | средняя (латентность) | низкая | **почти всегда** |
| Compression | низкий по качеству, высокий по цене | экономия | средняя | длинные чанки |
| Query rewriting | средний | низкая | низкая | разговорные запросы |
| Multi-query | средний | средняя | низкая | короткие вопросы |
| HyDE | средний | высокая (генерация) | средняя | вопрос не похож на документ |
| Decomposition | высокий на сложных | высокая | средняя | многошаговые вопросы |
| Adaptive routing | средний | экономия | средняя | смешанный поток |
| Self-RAG / reflection | средний (меньше галлюцинаций) | +1 вызов | средняя | строгие факты |
| CRAG + web fallback | высокий на «вне базы» | высокая | высокая | открытые источники обязательны |
| Agentic RAG | высокий на сложных | очень высокая | высокая | аналитика, многошаговые задачи |
| GraphRAG | высокий на связях | очень высокая | очень высокая | графовые вопросы |
| RAPTOR | средний на обзорных | высокая | высокая | огромные корпуса |
| Semantic chunking | средний | средняя | средняя | длинные неоднородные тексты |
| Кэш (точный + семантический) | 0 (но сохраняет качество) | −100% на повторах | низкая | **всегда** |

## 4. Что выбрать для Partner-Agent

База: материалы компании (10–500 документов), открытые страницы, ответы с
обязательными цитатами, интерфейс чата, требования «быстро, экономно, умно».

### Уровень 1 — уже реализовано

- hybrid-поиск (dense + BM25 + RRF);
- entity boost по продуктам и людям;
- карточки знаний (компания, продукт, человек, FAQ, новость);
- авто-контекст (карточка + 3 фрагмента) вместо лишних вызовов;
- обязательные цитаты и fallback «в материалах нет»;
- кэш ответов с TTL, разделением по языку и режиму;
- два режима: «Мышление» и «Быстро»;
- профиль компании `agent.json` — поведение без правок кода.

### Уровень 2 — следующие по соотношению «эффект / цена»

1. **Cross-encoder rerank** top-20 → top-5. Ожидаемо самый большой прирост
   точности на реальных вопросах; добавляет 50–150 мс, не требует менять индекс.
2. **Contextual headers** при индексации: к чанку приписывать «компания · раздел ·
   продукт». Дёшево, снимает главную причину неверных ответов.
3. **Reflection по цитатам**: один дешёвый проход «у каждого факта есть источник».
   Ловит галлюцинации без полного Self-RAG.
4. **Adaptive routing**: простые вопросы — без поиска (кэш/карточка), средние —
   один поиск, сложные — план и несколько инструментов. Экономит вызовы.
5. **Prompt caching** у провайдера и дешёвая модель для rewrite: прямая экономия.

### Уровень 3 — по потребности

- **Parent-child** — если появятся длинные регламенты и договоры.
- **Decomposition** — если пойдут вопросы-сравнения на 3+ условия.
- **Text-to-SQL** — если партнёр даст прайс-лист таблицей и нужны точные расчёты.
- **GraphRAG** — только если появятся вопросы про связи («кто отвечал за проект X»).
- **CRAG + web fallback** — если разрешат ходить в открытый интернет в рантайме.
- **Multimodal** — если пришлют презентации со схемами.

### Чего делать не стоит

- **Agentic-цикл на каждый вопрос** — дорого и медленно; он уже ограничен режимом
  «Мышление» и профилем `limits.max_steps`.
- **GraphRAG на 20 документах** — стоимость выше пользы.
- **Fine-tuning эмбеддингов** до накопления реальных вопросов — не на чем учить.
- **Много-уровневые суммаризации (RAPTOR)** — база слишком мала.

## 5. Как измерять, что метод действительно лучше

Без замера выбор методов превращается во вкусовщину.

1. **Золотой набор**: 50–100 реальных вопросов партнёра с эталонными ответами и
   документами-источниками. Собрать вместе с представителями компании.
2. **Метрики поиска**: Recall@5, MRR@10 (нашли ли нужный фрагмент).
3. **Метрики ответа**: faithfulness (каждое утверждение подтверждено источником),
   answer relevance, доля ответов «в материалах нет» там, где действительно нет.
4. **Метрики эксплуатации**: p50/p95 задержки, токены на ответ, цена за 1000
   вопросов, доля кэш-попаданий.
5. **Ablation**: включать методы по одному, сравнивать на одном наборе. Откат
   любого метода — одна настройка, а не переписывание.

Ориентир приёмки: ≥90% ответов с корректной цитатой, ≤5% выдуманных фактов,
p95 быстрого режима ≤6 с, стоимость ответа ≤2 500 токенов.

## 6. Антипаттерны

- **Один чанк = один факт без контекста** → ответы «по обрывкам».
- **Слишком большой top-k** → модель тонет в контексте, растёт цена.
- **Ссылки «на документ» без цитаты в тексте** → невозможно проверить.
- **Дублирование источников в индексе** (сайт + PDF того же текста) → выдача
  заполняется одним и тем же.
- **Кэш без TTL** → устаревшие цены и условия.
- **Промпт с жёсткими требованиями под одну компанию** → нельзя переиспользовать.
- **Веб-контент без санитизации** → промпт-инъекции из страниц.

---

## 7. Итоговая рекомендация

Для Partner-Agent самый эффективный набор на ближайший этап:

**hybrid + entity boost + cross-encoder rerank + contextual headers +
reflection по цитатам + adaptive routing + кэш и prompt caching.**

Это даёт максимум качества на малой базе при умеренной цене и низкой сложности,
не требует GPU и тяжёлой инфраструктуры. Тяжёлые методы (GraphRAG, RAPTOR,
полный agentic, fine-tuning) имеют смысл только при росте базы и появлении
соответствующих типов вопросов — и тогда их можно включить как отдельные уровни,
не ломая текущую архитектуру.
