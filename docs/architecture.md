# Архитектура Partner-Agent

## 1. Задача кейса

Нужен ИИ-ассистент, который отвечает на вопросы о компании-партнёре по открытым
источникам и материалам, присланным представителями компании, сохраняет контекст
диалога и показывает, откуда взят каждый факт.

| Требование кейса | Где реализовано |
|---|---|
| Сбор и структурирование информации | `domain/sources.py`, `domain/entities.py`, `ingest.py` |
| База знаний на RAG | `engine/` (chunking, bm25, embeddings, vectorstore, retriever) |
| Механизм поиска и обработки | `domain/retriever.py` (dense + BM25 + сущности, RRF) |
| Формирование ответов | `agent.py`, `prompts.py` (инструменты, цитаты) |
| Интерфейс с контекстом диалога | `api.py` + `web/` + SQLite (`engine/db.py`) |

├───────────────────────────────┬────────────────────────────────────┤

## 3. Путь данных

### Сборка индекса (`python ingest.py`)

```
data/company/**
   │  sources.py: PDF→текст, DOCX→текст, HTML→текст, MD/TXT как есть, JSON/CSV
   │  urls.txt → httpx + BeautifulSoup (заголовок, текст без меню и футера)
   ▼
RawSource[]        (kind: about/product/person/faq/news/doc/web)
   │  entities.py: карточки + реестр сущностей
   │    продукт  → «Продукт X» + описание
   │    человек  → «Сотрудник X» + роль
   │    FAQ      → пары «Вопрос/Ответ» (регулярка Q/A, Вопрос/Ответ)
   │    новость  → заголовок + дата + лид
   ▼
Document[]  →  Chunker (RecursiveCharacterTextSplitter, 900/120)
   ▼
Chunk[]  →  BM25 (лексика)  +  fastembed → Chroma (плотные векторы)
   ▼
storage/index/{chunks,bm25,entities,meta}.json + storage/chroma/
```

### Ответ на вопрос (`POST /api/chat`)

```
вопрос
  │ 1. язык вопроса (lang.py) и режим (thinking / fast)
  │ 2. кэш ответов: точное совпадение → семантика (cosine + Jaccard) → сущности
  ▼
контекст: карточка компании + найденные продукт/человек + топ-3 фрагмента
  ▼
модель:
  thinking → цикл инструментов (search_knowledge, company_profile, find_product,
             find_person, find_faq, kb_stats, plan) до 6 шагов
  fast     → один вызов по короткому промпту, без инструментов
  ▼
ответ с цитатами → SSE (start, step, reasoning_delta, tool_call, tool_result,
                          delta, sources, done) → SQLite
```

## 4. Профиль компании (гибкость без правок кода)

Всё предметное поведение вынесено в `data/company/agent.json` и превращается в
`AgentProfile` (`domain/agent_profile.py`). Код содержит только нейтральные
умолчания; конфиг переопределяет любое поле.

```
agent.json ──► build_profile() ──► AgentProfile
                                   ├─ persona (роль, аудитория, тон)
                                   ├─ style (заголовки, пункты, таблицы, длина)
                                   ├─ citations (обязательность, формат, название блока)
                                   ├─ rules / topics.focus / topics.avoid
                                   ├─ fallback / cta / glossary / language
                                   ├─ retrieval (top_k, context_hits, excerpt_chars)
                                   ├─ limits (max_tokens, fast, local, max_steps)
                                   ├─ tools (какие инструменты доступны)
                                   └─ branding (заголовок, примеры, аватар)
                                          │
                     prompts.py ◄─────────┤  промпты собираются из профиля
                     agent.py   ◄─────────┤  лимиты, инструменты, fallback
                     api.py     ◄─────────┘  GET /api/agent/profile → брендинг UI
```

Почему это важно для кейса:

- **любая компания** подключается заменой данных и конфига, без релиза кода;
- **требования к ответу** (тон, структура, цитаты, запреты) меняются в одном JSON;
- **экономия и скорость** регулируются `retrieval` и `limits`, а не правкой промпта;
- **интерфейс** подстраивается под бренд через публичный профиль.

## 5. Ключевые решения

- **Гибридный поиск, а не только эмбеддинги.** Названия продуктов и должности
  часто ищут точной строкой; BM25 закрывает это, эмбеддинги — перефразировки,
  буст по сущностям поднимает карточку продукта/человека в выдаче. Слияние — RRF.
- **Карточки вместо «сырых» файлов.** Один документ про компанию не должен
  размазываться по десяткам чанков; FAQ режется на пары, чтобы ответ находился
  целиком. Сырые материалы остаются отдельными документами (`doc`, `about`, `web`).
- **Обзор базы.** Первый документ `overview` перечисляет компанию, продукты,
  команду и свежие новости: он помогает на общие вопросы и служит fallback.
- **Кэш ответов.** Повторный вопрос не стоит токенов. Ключ включает сборку индекса,
  режим и язык; TTL и лимит записей не дают кэшу устареть.
- **Один клиент LLM на два провайдера.** DeepSeek и Ollama совместимы по протоколу;
  для локальной модели отключается reasoning и включается однократный вызов.
- **Язык ответа = язык вопроса.** Директива ставится последней строкой промпта,
  иначе русскоязычный контекст перетягивает ответ.

## 6. Что перенесено из первой части (s2ze.com)

| Модуль | Изменения |
|---|---|
| `engine/chunking.py` | без изменений (Document вынесен в `engine/types.py`) |
| `engine/bm25.py`, `tokenize.py`, `embeddings.py`, `vectorstore.py` | без изменений |
| `engine/llm.py` | провайдер и модель берутся из настроек, thinking отключаем для Ollama |
| `engine/db.py` | без изменений (сессии, сообщения, кэш, миграции) |
| `engine/answers.py` | без изменений (TTL, язык, режим) |
| `engine/lang.py` | без изменений (язык, fallback) |
| `engine/compat.py`, `logbook.py` | без изменений |
| `web/` | перенесён целиком, заменены тексты и брендинг |
| `retriever`, `agent`, `prompts`, `api`, `loaders` | написаны заново под предметную область |

## 7. Расширение под реального партнёра

1. Заменить содержимое `data/company/` материалами компании (структура папок та же).
2. Заполнить `profile.json` и `urls.txt`.
3. `python ingest.py` — пересобрать индекс.
4. Проверить карточки: `GET /api/kb/stats`, `POST /api/retrieve`.
5. При необходимости добавить новые типы карточек в `domain/entities.py`
   (например, «кейс клиента» или «сертификат») — достаточно нового `kind` и папки.

## 8. Ограничения и что дальше

- Нет доступа к CRM/ERP партнёра: ответы только по присланным материалам.
- Изображения и таблицы из PDF не распознаются как структура — попадают текстом.
- Для больших сайтов стоит добавить ограничение глубины обхода и Sitemap-парсер
  (в первой части есть готовый `site.py`, который можно перенести).
- Аутентификации нет: это внутренний демо-стенд.

## 9. Какие ещё бывают RAG и что выбрать дальше

Полная карта методов, сравнение по эффекту/цене/сложности и план измерений —
в отдельном документе [rag-methods.md](rag-methods.md).

Коротко о рекомендуемом следующем шаге: **cross-encoder rerank**, **contextual
headers**, **reflection по цитатам**, **adaptive routing** и **prompt caching**.
Это максимальный прирост на текущей базе при минимальной сложности. Тяжёлые
подходы (GraphRAG, RAPTOR, полный agentic, fine-tuning) имеют смысл только при
росте корпуса и появлении соответствующих типов вопросов.
